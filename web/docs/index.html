The Emote System

3D cosmetics and Fortnite-style emotes on vanilla Minecraft.

No mods. No resource pack. Every hat, cape, wing and dance is drawn entirely by server-sent packets — the client just renders ordinary vanilla display entities and armour stands.

Vanilla — no resource pack Built on PacketEvents Paper 1.21 Works on Java & Bedrock

What it is

Most servers ship a resource pack to show custom cosmetics. That forces a download on every player and breaks on Bedrock. LemonPvP takes the opposite route: it never sends a pack at all. Instead it spawns vanilla display entities (item_display, block_display) and armour stands as pure packets, addressed only to the players who should see them, and drives their appearance and motion frame by frame.

The result reads like a modded server but runs on a stock client — a Java player and a Geyser/Bedrock player see the same cosmetic. This page explains the five techniques that make it work, plus the emote layer built on top.

Why packets, not real entities? A packet entity has no server-side tick, no physics and no persistence. It exists only in the viewer's client, so a thousand capes cost the server almost nothing and never desync a save.

The pipeline

A cosmetic is one display entity glued to a wearer. Five concerns, each a self-contained step:

1 Spawn a display entity by packet

A display entity is spawned with a single Spawn Entity packet. The entity id comes from a client-safe fake-id allocator; the entity type is ITEM_DISPLAY or BLOCK_DISPLAY. The manager sends it to every player currently tracking the wearer, so it appears and disappears with range exactly like a real entity — but nothing is created server-side.

2 Transform & scale

A display entity carries a render transform: the client draws its model through an affine matrix built from four parts. For each model vertex v the client computes

v′ = translation + leftRotation · ( scale ⊙ ( rightRotation · v ) )

First rotate the raw model (rightRotation), then scale it per-axis (scale, ⊙ = component-wise multiply), rotate again (leftRotation), and finally move it (translation). Two rotations bracket the scale because that is the singular-value-decomposition form of an arbitrary 3×3 matrix — but for a cosmetic one rotation is plenty, so rightRotation stays identity and the tilt goes in leftRotation.

3 Custom textures via player heads

This is the trick that gives detailed 3D hats with no pack. Mojang stores a skin as a signed textures property on a GameProfile: a Base64 blob that decodes to a small JSON pointing at a textures.minecraft.net URL. Put that profile on a player_head item, render it on an item-display, and the vanilla client downloads and draws that skin on the head model — entirely client-side, entirely vanilla.

4 Latency-free movement tracker

If you move a cosmetic from a server tick, it trails the wearer by a tick — visibly rubber-banding when they sprint. The fix is to update it the moment the movement arrives. A PacketEvents listener intercepts the player's inbound position packet on the Netty I/O thread, before the server has even ticked, and immediately teleports the cosmetic to the new coordinates.

Thread safety. The listener never touches live entity state off-thread: it reads the coordinates straight from the packet and uses a cached world + last yaw, then sends packets — which PacketEvents permits off the main thread. That keeps the cosmetic pixel-locked to the body without risking async access.

5 Smooth animation via client interpolation

Display entities have a built-in tween. Set metadata index 9 (interpolation_duration) to N ticks and the client smoothly interpolates from its current transform to the next one over those N ticks. So the server sends a fresh rotation only every few ticks, and the vanilla client fills every frame in between — a cape sways and wings flap at the player's full frame-rate for almost no bandwidth.

Fortnite-style dance emotes

Emotes reuse the same idea one layer up. When a player emotes, they are frozen and made invisible (a potion effect, no particles), and a packet-only armour-stand body double takes their place — wearing their own head and armour. The double then performs a dance by re-posing its limbs every two ticks through the armour-stand pose metadata (head, body, both arms, both legs), with spins driven by teleport yaw and a light note-block beat underneath.

Each dance is a pure function of time: poseAt(tick) returns the six limb rotations for that frame. Keyframes are cheap sine mixes, so they loop seamlessly and stay easy to tune. Here is the WAVE emote — the right arm sweeps while the head tilts along:

Armour-stand poses (for emotes) live at indices 16–21: head, body, left arm, right arm, left leg, right leg — each a degree ROTATION vector.
