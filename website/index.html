Open-source Paper fork for Minecraft

Swap code on a running Paper server.

PaperSwap hot-swaps modules, updates plugins and patches Paper's own code while the server keeps running, whenever the JVM can do it safely. When it can't, PaperSwap tells you to restart instead of guessing.

Excerpt from the CI job "Spear fix as live core patch (1.21.11)" on a standard JVM with -javaagent:paperswap-agent.jar. Omitted lines are marked ⋮.

  1. Scan

    fork live scan lists what is waiting: modules, plugin updates and core patches. Nothing runs just because a file appeared.

  2. Plan

    fork live update <name> checks the JVM, the running build and every class, then shows exactly what would change.

  3. Confirm

    Only confirm at the console changes the server, and only for the SHA-256 that was checked.

  4. Verify or roll back

    PaperSwap reads the running bytecode back from the JVM. fork live rollback restores the previous classes or plugin JAR.

Three ways to change a running server

Modules, plugins and the server itself.

Each path has its own switch, its own checks and its own limits. You decide which ones a server may use.

Hot-swappable modules

Extensions written against the PaperSwap API, each in its own class loader. Load, enable, replace and unload them at runtime.

Safety net
A failed swap keeps the old version running. Listeners, tasks, commands and services are tracked and released.
Limit
The module instance is replaced. It is not a JVM hot swap.

Live plugin updates

Ordinary Bukkit plugins from plugins/update. Every update is checked first: descriptor, main class, class versions and dependencies.

Safety net
If loading fails, the previous JAR is restored. Leftover listeners, tasks and threads are reported.
Limit
Paper plugins, plugins with lifecycle API or active dependants always need a restart.

Core patches

Change Paper or Minecraft source, build a .swappatch with Gradle and apply it through java.lang.instrument.

Safety net
Build id, SHA-256 and every class are checked before; the running bytecode is read back after.
Limit
Standard JVMs change method bodies only. Structural changes need JetBrains Runtime.

Safe by default

Asleep until you wake it.

A fresh PaperSwap build behaves like Paper. Everything that loads or changes code is switched off until you turn it on in config/paperswap.yml.

  • Runtime enabled: falseNo background activity, no extra threads, no commands.
  • Console onlyCode-changing permissions default to nobody. RCON does not count as the console.
  • No folder watchingNo auto-load and no downloads. A new file does nothing until an operator asks for it.
  • No network portThe agent attaches through the JDK's local socket. An exposed JDWP debug port is reported as a warning.
  • Production patch profileOnly allow-listed patches with a matching SHA-256 file. Changes are recorded in the audit log.

Honest about the limits

What PaperSwap will not pretend.

Live changes are powerful and narrow. PaperSwap names its limits in the console, in the docs and on this page.

  • No universal live patchingStandard JVMs (Temurin, OpenJDK, Oracle) only change method bodies. Added methods or fields need JetBrains Runtime with -XX:+AllowEnhancedClassRedefinition.
  • Rollback restores code, not stateObjects, static fields, caches, threads and anything a patch already did stay as they are. Static initialisers do not run again.
  • Verified means bytecode"Verified" proves the JVM runs exactly the patched bytecode. Whether the code is right is for your test of that code path.
  • Plugins have no official unloadPaperSwap uses Paper internals that exist in all four versions. If they are missing, it answers "restart only".
  • Patches end with the processAfter a restart the server runs its JAR again. Ship a new build for anything permanent.
  • No sandboxA module runs with the server's rights. Whoever may write to paperswap/modules/ effectively has shell access.

Tested on real servers

Three test levels, never mixed up.

  • Unit and integration testsRuntime core with real module JARs, real class loaders and the real agent, on Temurin 21 and JetBrains Runtime 21 and 25.
  • Paper buildEvery fork build runs Paper's own test suite against the PaperSwap server, for all four versions.
  • Live server testsEach server is started and driven through its console: modules, plugin updates, core patches, dynamic attach and rollback.

Not automated yet: real player connections, load tests with players, proxies, Windows and macOS.

Get started

From source to your first swap.

Build a server

Pick a version folder. Paperweight fetches Paper at the pinned commit and applies PaperSwap's patches.

# 1.21.11: createMojmapPaperclipJar
cd versions/26.2
./gradlew applyAllPatches build createPaperclipJar

Switch it on

The first start writes config/paperswap.yml. Enable the runtime and restart once.

enabled: true
# test and development servers only
allow-runtime-deploy: true

Swap a module

Drop the JAR and its .sha256 into paperswap/modules/, then use the console.

fork module enable example-greeter
fork module reload example-greeter
fork module diagnostics example-greeter

Step-by-step guides for plugin updates, core patches and the agent are in the documentation.
